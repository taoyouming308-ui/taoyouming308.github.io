# Salon 订单明细并发版本保护

状态：独立分支、临时 PostgreSQL 与本机页面验证；未部署迁移/Edge，不接旧 App。本机新建/原请求恢复/列表重选草稿的多项目编辑已接入，改价/优惠/员工分配仍未开放。选单必须显式重新读取，不得自动刷新版本重试冲突写入，详见 `salon-order-list.md`。

## 规则与边界

- `salon_orders.edit_version` 初始为 0。订单更新，以及明细新增/修改/删除，都会在事务中推进版本；调用者不能通过赋值把它重置。版本是比较用的整数令牌，不是修改次数，每次整单保存可能推进多次。整数溢出拒绝事务，不归零。
- 创建后回读、保存后回读及原请求核对恢复时读取版本。保存携带这次读取的 `expectedVersion`，不在提交前偷偷读取最新版本，不把冲突自动改成强制覆盖。
- 员工 `order_lines` API 只接严格非负 32 位整数版本并调用 `salon_replace_order_lines_versioned`。事务沿用身份/当前权限、完整参数指纹、请求号与订单行锁；同一旧版本的不同请求只有一个可成功。版本检查在删除明细之前，失败回滚请求占用、明细、版本与业务审计。
- 完整指纹包含员工、组织、店、订单、明细、优惠原因和版本。原键重试先核验身份/完整参数，再返回原成功回执，不用已变化版本再次执行。改变版本/参数的同键请求拒绝；没有版本上下文的旧回执不能冒充新请求。
- 首次明确版本冲突禁用当前明细保存，保留原订单供只读核对；不自动重新取版本后保存。此前已有未知结果时，后续拒绝仍保留待核对清单。返回后继续执行既有完整明细回读，不把历史回执当作当前订单状态。

这是编辑接口的并发保护，不是整套协同编辑或订单锁单产品。只读原单查询不绑定编辑器。旧 `salon_replace_order_lines` 保留供内部兼容与既有 SQL 测试使用，没有版本比较，不能再接到页面或作为新编辑接口；上线前需审计/收敛所有内部调用。其明细变动仍会推进版本，令新接口的旧快照失效。后台批量事务还需遵守请求、订单及明细的统一锁顺序，不能把本批称为全业务死锁验证。

## 权限与数据

不增加浏览器表权限或密钥。新函数和触发器为 SECURITY INVOKER、空 search_path；撤销 PUBLIC/anon/authenticated 执行权，只供 service_role 通过现有员工身份及门店授权调用。无新增表，不改变既有 RLS。只添加版本列，不读取或迁移真实顾客/会员/资金数据。

金额、优惠权限、员工归属、商品启用、审计和原有计算逻辑沿用旧函数；新入口另补 SQL NULL 明细拒绝。客户端 sessionStorage 仍只有原请求元数据，版本和业务正文随冻结请求保存在当前页内存，不增加敏感持久化字段。

## 验证

- `test-salon-order-version.mjs`：版本类型、完整指纹、先重放后版本比较、删除前检查、invoker/触发器契约。
- `test-salon-order-version.cjs`：两个实际 PostgreSQL 会话同时保存/同键重试；旧版本拒绝、状态改变再改回、直接明细修改、版本不能重置、失败回滚、撤权后重试拒绝、浏览器权限拒绝；1280/390 页面携带原版本，冲突后不覆盖、不自动重发。
- 已有工作台、原请求查询、刷新/回读恢复、整单明细匹配及主数据/资金/顾客事务均需回归；各项以测试回执为准。
- 已核对 Supabase 变更摘要、函数权限及 PostgreSQL 行锁文档。CLI 2.109.1 创建本地迁移；`db advisors --local` 因默认本地实例不可连接未完成，没有改连生产。临时 PostgreSQL 回放不能替代真实 Auth/Edge、完整 Advisor 或上线验收。
