# 退款审批与原支付核对

状态：独立开发分支、本机合成数据；不部署、不合并原三个 App。

## 本批完成范围

本店申请列表 → 载入申请/项目明细/原支付分配 → 填写审批意见 → 人工确认批准或拒绝 → 回读审批结果；丢包同键重试，刷新后只读核对原请求。

只处理已有申请。没有申请创建、实际退款、会员退回、商品返库按钮。**批准不是退款成功**，不能把审批状态当资金、库存或净收入凭证。

## 页面与权限

- 按待审批/已批准/已拒绝/已执行/已取消或全部筛选，每页 50 条，ID 游标分页。列表只返回申请 ID、原单 ID、申请金额和状态。
- 载入展示申请类型/原因/申请人编号、订单当前状态/原应收/已执行退款额、项目退款数量与金额、原支付编号/方式/金额/状态、退款分配；次卡显示原支付次数与申请退次数。
- 不读取手机号、顾客姓名、会员账户 ID 或余额、电子交易凭证、整店财务明细。
- 申请人不能审批本人申请。按钮只作交互提示，实际权限由服务端重新校验。查询需要 orders.refund_read，详情另需 orders.read；审批还需 orders.refund_approve。默认基础合成角色不追加这些权限，专项测试单独准备双人员工夹具。
- 金额按整数分、次数按整数千分位检查，防不一致分配直接批准。不满足批准条件的合法快照仍可经人工核对后拒绝；格式或范围异常则不能继续。
- 选择、筛选、重新查询、切店、重连、退出及业务提交清除旧快照/意见；输入只在内存。未知请求锁定其他写入，不存金额或审批载荷至浏览器持久存储。

## 数据库与 API

CLI 创建 20260908051941_salon_refund_review_workbench.sql：

- refund_queue → salon_list_refund_review_queue，最小字段与索引支持游标分页。
- refund_detail → salon_get_refund_review，范围内联结原单/原支付，拒绝缺失或跨单分配，STABLE/INVOKER、空 search_path、只授 service_role；READ ONLY 事务可执行。
- refund_review 改为 salon_review_refund_checked，必须携带 expectedSnapshot。冻结刚查看的申请、订单版本、项目与原支付字段；事务按退款申请 → 原订单 → 支付 ID 顺序锁定后比较，变化即拒绝，不自动刷新覆盖。
- 复用现有 refund_review 动作，全部参数进入员工请求指纹。成功原键重试返回历史回执；更换人员/决定/意见/快照则不能复用原键。
- 批准前检查原单可退款状态、当前可退总额、两种分配合计及原支付对应；累计 submitted/approved/executed 支付退款金额或次卡次数不能超过原支付。新增原支付分配索引。该保护不修改既有申请/执行函数；旧入口仍需上线前统一收敛。
- 审批只更新该申请的审批字段，并追加审计与请求完成记录；不调用退款执行、不改支付/订单/库存/会员/业绩。审计异常整笔回滚。

旧 salon_review_refund_request 保留内部兼容，不作为本机新页面入口。新的 API 参数是未发布开发接口契约变化，不代表已迁移任何线上调用方。

## 结果恢复

成功后核对申请 ID、原单、审批人、决定与审批意见，随后回读当前详情才清除元数据清单。回读失败关闭写重试，只允许查询原请求。

request_lookup 新增 refund_review：只返回当前员工/店/组织的已完成请求，联结具体申请；历史决定与当前状态分开展示。当前已取消或已执行不会重做审批。当前审批人异常或申请回到 submitted 则保留清单人工核对。旧回执缺少新增关联字段时不强行恢复。

刷新后的 sessionStorage 仍只有 operation/requestKey。查询不到不等于失败，不能新建审批。关闭标签页、清空存储及跨设备恢复尚未支持。
