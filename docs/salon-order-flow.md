# 整单状态处理：开单到待收银

状态：独立分支、本机合成数据验证，未部署。不是完整服务现场或收银闭环。

## 页面规则

- 新建/重选草稿，先保存项目明细，然后“确认开单”。空单或未保存修改不开放状态操作。
- 已开单可“开始服务（整单）”或“转待收银（不收款）”；服务中可“转待收银”。保留既有后端允许已开单直接待付款的路径，不自行要求商品订单先开始服务。
- 列表中的 opened/in_service/awaiting_payment 可“载入订单处理”，始终重新读取当前记录及版本。普通“查看”不绑定处理对象。
- 每次状态提交前确认订单号与操作；不自动保存草稿，不在后台推进状态。当前页面没有取消、退款、支付或会员扣款按钮。
- 整单状态与 `salon_order_lines.service_status` 不同。这批不把项目标为完成、不分配员工、不替代现场交付确认；待收银不是已收款。明细开始/完成、服务证据与收银仍待开发。

## 服务端边界

`order_status` 改走 `salon_set_order_status_versioned`，强制读取时的整数 expectedVersion。新增函数保留原状态图、空单规则、取消原因与审计，增加锁定订单后的版本比较。版本纳入完整操作者/参数指纹；原键成功重试先返回原回执，不能改参数或版本重放。

旧 `salon_set_order_status` 仍 service_role-only，保留内部兼容；API 不再使用它。上线前须收敛或退役所有无版本内部写调用，与明细旧入口一并审计。没有增加浏览器表权限。新增函数 INVOKER、空 search_path、仅 service_role 可执行，仍重新校验本店 orders.write。

`request_lookup` 和本机最小清单扩展至 order_status。未知结果继续冻结原键/参数；刷新只保存操作类型/请求号，不保存目标状态或业务正文。成功写入还须匹配订单 ID、回执目标状态、当前回读状态后才清除清单；当前状态已经被后续操作改变时保留清单，使用只读核对历史结果与当前状态，不自动重发。

版本冲突关闭状态及明细保存，不自动刷新版本后再次执行。用户须明确重新选单核对；切店、退出、会话失效与离开编辑清除当前处理对象。未知结果期间列表与处理均锁定。
