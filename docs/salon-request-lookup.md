# Salon 未知结果核对：只读接口第一批

状态：独立分支、本机合成数据验证；尚未部署。员工本机页已增加同标签页刷新的待核对清单与人工查询入口，边界见下文。

## 支持范围

员工 API 新增 `request_lookup`，输入 `storeId`、原 `requestKey`、`targetOperation`。仅支持 `customer_create`、`order_create`、`order_lines`，不支持顾客端、收银、退款、充值或批量搜索。

身份由现有 API 验证并解析实际员工/组织/所选门店；忽略客户端伪造身份参数。数据库要求当前门店相应资源的 read 和 write 权限，并精确匹配原员工、原组织、原店、原请求号和操作类型。曾经有权限不等于现在有权限。

使用现有请求表的 `(organization_id, request_key)` 唯一索引查询，不新建表、不增加浏览器表权限、不认领请求、不重放写操作、不修改业务数据。RPC 为 STABLE / SECURITY INVOKER，空 search_path，仅 service_role 可执行；API 仍可按原规则记录不含业务正文的访问元数据。

## 返回语义

| status | 含义 | 安全处理 |
| --- | --- | --- |
| committed | 找到有操作者证明、已完成且有有效资源编号的历史请求回执 | 不再重新执行；按编号通过当前业务查询核对现状 |
| unconfirmed | 未找到可向当前操作者确认的回执 | 继续保留待核对状态，不能据此新建或重发 |

`committed` 仅额外返回 `resourceType`（customer/order）、`resourceId`（十进制字符串）、`completedAt` 和原操作类型。**这不是当前订单状态、金额或支付成功凭证**；订单之后可能被修改或撤销，应另查业务页面。

`unconfirmed` 不区分不存在、事务未提交、回滚、缺少身份信息的旧回执、其他人/其他店/其他操作的请求。没有记录也可能是请求尚未到达服务器，不能证明旧请求将来不会提交。接口不返回 failed、自动补单建议或可安全重新提交标记。

只输出白名单字段，不返回 response_json 全文、请求指纹、顾客姓名/电话、订单明细/备注、金额或余额。原请求号与 HTTP 追踪 requestId 是不同标识，不能混用。

## 验证与边界

- `node scripts/test-salon-api.mjs`：操作/请求号严格白名单、伪造身份不生效、无效请求不调用数据库。
- `node scripts/test-salon-request-lookup.cjs`：临时 PG + 真实本机 HTTP + 统一客户端；丢失写入响应后新合成会话查询，三类最小回执，读写权限分别撤销、停职、跨人/店/组织、旧回执、提交中与回滚、read-only 事务及查询前后业务快照不变。

## 同标签页刷新恢复（2026-09-07）

`recovery-journal.mjs` 使用 sessionStorage 专用键 `salon.pending.v1:组织ID:门店ID:员工ID`，正文仅为版本和操作类型/原请求号。只接三类已支持操作，不保存令牌、业务正文、顾客资料、金额或返回回执。其他 App 的键不读写。

1. 发送三类写入前先写清单并回读校验。存储拒绝、满额或写入无效则不发送。
2. 同页网络结果未知仍沿用已有冻结参数重试；刷新后不保存、不重造业务参数，也不自动重发。
3. 刷新/重新连接后经现有会话与门店验证，只展示当前员工/当前门店的清单；未连接时不展示编号。存在待核对项则禁止新业务，保留独立只读查询入口。
4. 人工查询 committed 后，再读取当前业务记录。订单按实际状态恢复编号，只有草稿可继续保存明细；顾客必须出现在当前授权列表中。当前记录无法核对则保留清单，不自动建档/补单。
5. unconfirmed、请求失败、异常回执、当前记录读取失败均不删除清单。写入与当前记录回读均成功，或首次尝试收到明确 4xx 拒绝且此前从未出现未知结果，才清除对应项；已有未知结果后再遇到拒绝（如撤权）仍保留，因为拒绝不能证明第一次未提交。清除失败也不允许再次创建业务。
6. 格式损坏保持原始存储不覆盖，显示通用错误、不回显原内容；没有一键重置、过期自动删除或容量淘汰。需要保留现场后人工核对。

限制：这是单标签页、同源、本机临时服务仍运行时的刷新恢复。关闭标签页、浏览器清理/驱逐存储、临时数据库重启、复制标签页、跨设备、顾客端与其他操作不保证恢复。客户端清单不是权限凭证，也不能防止人为删除后重新提交；服务端身份、作用域和幂等规则仍是最终边界。正式持久化待办与人工异常处置尚未实现。

测试：`test-salon-recovery-journal.mjs` 覆盖最小字段、三维隔离、损坏不覆盖和存储失败；`test-salon-recovery-workbench.cjs` 用 1280/390 浏览器与临时 PG 验证三类响应丢失后的刷新查询、不重复业务、未知/异常回执继续锁定及存储失败零发送。

## 写入成功、回读失败的交接保护（2026-09-08）

三类写入即使收到成功回执，也不能在后续读取之前清除清单。建档须在当前授权列表找到对应 ID；创建草稿须读取同一订单当前状态；保存明细须读取同一订单和所选项目。订单是否可编辑以当前读取的 draft 状态为准，不以历史创建回执为准。

回读失败时关闭原写入重试，保留最小元数据与新业务锁定，开放独立“只读核对原请求”。同页、刷新或重新连接后沿用既有核对路径，不重放已确认成功的写入。重复回读失败、返回其他订单或授权列表未找到顾客均不能清除。此处的回读只是读取时刻的状态，不能代替下一次数据库写入的并发校验，也不提供支付成功证明。

`test-salon-readback-recovery.cjs` 使用 1280/390 Chrome 和临时 PG，分别在实际成功写入后模拟读取不可达、缺失顾客和错误订单 ID，核对重复读取失败仍保留、刷新后只读恢复、三类写入各仅产生一份记录；另在创建/明细提交后、回读前推进合成订单到 opened，确认不再开放草稿编辑。仍不覆盖关闭标签页或跨设备。

实施依据：[Supabase 函数权限与 invoker](https://supabase.com/docs/guides/database/functions)。
